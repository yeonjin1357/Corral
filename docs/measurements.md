# 측정 기록

## 1단계 — Windows 부하 측정 (2026-11-06)

### 환경

- CPU: Intel Core i9-12900 (논리 코어 24개), RAM 63.7 GB, Windows 11 Pro
- 측정 중 떠 있던 것: 개발 서버 포트 11개(vite 3개, java 서버 4개 프로세스·포트 6개, 게이트웨이 2개, Gradle 데몬 2개), Claude Code 세션 5개
- 대상: `npm run build` 결과물을 `electron .` 으로 실행, 창을 닫아 트레이에만 둔 상태(수집 주기 30초 = 갱신 주기 "보통")
- 방법: pitwall 의 electron 프로세스 전체(main·GPU·network·renderer)의 CPU 시간과 메모리를 1분마다 10분 동안 기록. 수집에 쓰는 PowerShell 은 매번 새로 떴다가 끝나므로 따로 5번 실행해 1회 비용을 쟀다.

- 수집 1회 걸리는 시간: 약 1.0초.
- 창을 열어 두었을 때 갱신 간격: 약 5.9초(주기 5초 + 수집 0.9초).
- 창을 최소화하면 갱신이 30초 주기로 바뀌고, 다시 열면 1초 안에 새로 수집한다.
- WmiPrvSE 는 관리자 권한 없이 성능 카운터(`\Process(WmiPrvSE*)\% Processor Time`)로 쟀다. 수집 없이 15초를 잰 값을 기준선으로 두고, 수집 10번을 하는 동안 늘어난 만큼을 수집 몫으로 봤다(1회 약 0.30초).
- 창을 열어 두면(약 6초마다 수집) 수집 비용은 코어 1개 기준 약 14%, 전체 CPU 대비 약 0.6% 다.
- 메모리 수치(아래)는 측정 당시의 작업 세트 기준이다. 이후 앱이 보여 주는 프로세스 메모리는 작업 관리자 "메모리" 열과 같은 전용 작업 세트로 바뀌었다.

### 수집 시간을 줄인 과정

처음에는 수집 1회에 약 5.0초(PowerShell CPU 약 1.05초)가 걸렸다. 나눠서 재 보니 다음 두 곳이 대부분이었다.

1. `Get-NetTCPConnection` 이 약 2초 → netstat 과 같은 OS API(`GetExtendedTcpTable`)를 C# 보조 코드로 직접 불러 몇 ms 로 줄였다. 실패하면 `Get-NetTCPConnection` 으로 대신한다. 결과는 같았다(LISTEN 56건 일치).
2. 675 KB 짜리 JSON 한 줄을 PowerShell 출력으로 내보내는 데 약 2초 → UTF-8 바이트를 표준 출력 스트림에 직접 쓰게 바꿨다.

C# 보조 코드는 앱 데이터 폴더(`%APPDATA%\pitwall\pitwall-native-<해시>.dll`)에 한 번만 컴파일해 두고 다시 쓴다.

### 메모리가 목표를 넘는 원인과 조정안

Electron 앱의 기본 프로세스 4개만으로 working set 이 약 375 MB 다. pitwall 의 데이터는 작다(main 프로세스 안의 스냅샷 몇 MB).

| 조정안 | 예상 효과 | 단점 |
| --- | --- | --- |
| 하드웨어 가속 끄기(`app.disableHardwareAcceleration()`) | GPU 프로세스 몫(약 90~115 MB) 대부분 절감 | 대시보드는 GPU 가 필요 없어 사실상 없음. 적용 후 다시 재야 함 |
| 창을 숨길 때 화면(renderer)을 닫고, 열 때 다시 만들기 | 숨긴 동안 약 90 MB 절감 | 다시 열 때 약 1초 걸림 |

두 가지를 모두 적용하면 트레이에 있는 동안 약 200 MB 안팎이 될 것으로 본다. 적용 여부와 효과는 다음 단계에서 다시 재서 정한다.

### macOS

작성자에게 Mac 이 없어 재지 못했다. 팀원 확인 때 같은 방법(활성 상태 보기의 pitwall 프로세스 합계, 10분)으로 잰다.

## 4단계 — Windows 부하 다시 재기 (2026-11-09)

- 대상: `electron-builder --win` 의 압축 풀린 결과물(`dist/win-unpacked/pitwall.exe --hidden`, 측정용 프로필·자동 실행·업데이트 확인 끔), 트레이만 띄운 상태(수집 30초 주기), 1분 예열 뒤 10분.
- 환경: 1단계와 같은 PC(논리 코어 24개, RAM 63.7 GB). 개발 서버 7개(포트 12개), 에이전트 4개, 무거운 작업 1개가 떠 있었다.

| 항목 | 결과 | 목표 | 판정 |
| --- | --- | --- | --- |
| pitwall 프로세스 CPU | 전체 CPU 대비 평균 0.007% (코어 1개 기준 0.18%) | 평균 1% 미만 | 충족 |
| 메모리(작업 관리자 "메모리" = 전용 작업 세트 합) | 57~73 MB | — | 참고 |
| 메모리(working set 합) | 212~229 MB (프로세스 4개) | 300 MB 미만 | 충족 |

- 이번 측정 스크립트는 수집용 PowerShell 자식을 하나도 잡지 못했다(samplerRuns=0). 그래서 위 CPU 에는 수집 비용이 빠져 있다. 1단계 값(1회 약 0.56초 + WmiPrvSE 0.30초, 30초마다 = 전체 CPU 대비 약 0.12%)을 더하면 약 0.13% 로 목표 안이다. 수집 비용은 다음 측정에서 다시 잡는다.
- 트레이 요약 창은 처음 열 때 만들고 숨기기만 해서, 열지 않으면 프로세스가 늘지 않는다(측정 중 4개).
