# pitwall 설계

- 작성일: 2026-11-06
- 상태: 승인됨 (2026-11-06). 디자인 기반은 Uptime Kuma.
- 레포: https://github.com/yeonjin1357/pitwall (공개, MIT)

## 1. 왜 만드나

AI 코딩 에이전트(Claude Code, Codex)를 여러 git 워크트리에서 동시에 돌리는 작업 방식이 늘었다(예: Orca 같은 병렬 에이전트 도구). 그러면서 코드 작성보다 **동시에 돌아가는 것들을 관리하는 일**이 더 피곤해졌다.

작성자 PC에서 실제로 본 상황(2026-11-06):

- 서로 다른 워크트리 3곳에서 개발 서버(vite)가 각각 포트 3000·3002·3003으로 떠 있고, 하나에 약 1GB씩 쓴다.
- node 프로세스 합계 약 16GB, Claude Code 프로세스 5개.
- 어느 포트가 어느 작업인지, 무엇을 꺼도 되는지가 한눈에 안 보인다.
- 프로젝트에 따라 타입 검사·빌드 같은 작업이 한 번에 8~12GB를 잡는다. 이런 작업이 겹치면 PC가 느려지거나 메모리가 부족해진다.

pitwall 은 **한 PC에서 돌아가는 개발 작업 전체를 한눈에 보여주고, 그 자리에서 정리까지 할 수 있는 상주 앱**이다. 이름은 F1 피트월(여러 차의 상태를 지켜보다가 필요하면 불러들이는 곳)에서 따왔다.

## 2. 누가 쓰나

- 작성자와 같은 팀 개발자들. 대부분 Claude Code, 일부는 Codex 도 같이 쓴다.
- Windows 와 macOS 를 둘 다 지원해야 한다.
- 공개 레포이므로 **특정 회사·프로젝트 전용이 아닌 범용 도구**로 만든다. 팀 밖 사람도 쓸 수 있어야 한다.

## 3. 목표 — 첫 버전에 아래 8개를 모두 넣는다

1. **에이전트 현황** — 실행 중인 Claude Code / Codex 세션, 어느 워크트리(작업 폴더)에서 도는지, 상태, 실행 시간.
   - Claude: 작업 중 / 권한 대기 / 유휴 같은 세부 상태까지.
   - Codex: "작업 중인지 아닌지" 수준. 세부 상태는 가능한 만큼만(§9).
   - Orca 같은 다른 도구가 이미 보여주는 정보라도 여기서 같이 보여줘도 된다. 겹침 때문에 빼는 것은 써보고 나서 판단한다(확정 아님).
2. **RAM 현황** — 전체 사용률과, 묶음별(개발 서버 / 에이전트 / 무거운 작업 / 기타) 사용량.
3. **포트 현황과 내리기** — 개발용으로 열려 있는 포트, 그 포트를 연 프로세스, 어느 워크트리 것인지, RAM. 여기서 바로 내린다.
4. **안 쓰는 포트 판단** — 두 단계로 표시한다(사용자 결정).
   - **정리 후보:** 그 포트의 워크트리에 실행 중인 에이전트가 없고, 그 포트에 접속이 하나도 없는 상태가 N분(기본 20분, 설정 가능) 이상 이어졌다.
   - **확인해볼 것(약하게 표시):** 에이전트는 없는데 브라우저 탭만 연결된 상태가 N분 이상 이어졌다. 개발 서버(vite 등)는 탭이 열려 있기만 해도 자동 새로고침용 연결을 유지하므로, 이걸 "사용 중"으로만 보면 탭을 안 닫는 사람에게 후보가 거의 안 뜬다.
   - 어느 단계든 내리기는 확인 창을 거친다. "최근 실제 요청이 있었는지"는 트래픽을 들여다봐야 해서 재지 않는다.
5. **남겨진 프로세스 정리** — 주인 에이전트는 끝났는데 남아 있는 프로세스(Playwright 브라우저, 테스트 러너 워커, 개발 서버 등)를 묶어서 보여주고 정리한다.
6. **무거운 작업 겹침 경고** — 사용자가 설정한 "무거운 명령" 패턴(예: 타입 검사, 빌드)이 동시에 2개 이상 돌고 **그리고** 남은 RAM 이 기준 이하일 때만 경고한다. RAM 이 넉넉한 PC 에서는 겹쳐도 조용하다. 막거나 줄 세우지 않는다.
7. **메모리 부족 경고와 정리 추천** — 남은 RAM 이 기준 이하로 떨어지면 알리고, "이것들을 끄면 약 X GB 확보"처럼 정리 후보를 묶어 추천한다.
8. **디스크 정리** — 끝난 워크트리(에이전트가 없고 브랜치가 머지된 것)의 의존성 폴더(`node_modules` 등) 용량을 보여주고 정리한다.
   - (Claude 판단) **찾는 법:** 에이전트·개발 서버가 한 번이라도 관찰된 저장소를 기억해 두고, 설정에서 저장소를 직접 추가할 수도 있다. 그 저장소들의 `git worktree list` 로 연결된 워크트리를 모두 찾는다. 끝난 워크트리는 돌고 있는 프로세스가 없어서 프로세스 관찰만으로는 못 찾기 때문이다.
   - (Claude 판단) **"끝남"의 기준:** 실행 중인 에이전트가 없고, 브랜치가 원격 기본 브랜치에 머지됐다.
   - (Claude 판단) **정리 범위:** 의존성 폴더만 지운다. 워크트리 자체는 지우지 않는다. 메인 체크아웃(연결된 워크트리가 아닌 원본 폴더)은 대상에서 뺀다.

## 4. 비목표 (첫 버전에서 하지 않는 것)

- 무거운 작업을 자동으로 기다리게 하거나 순번을 매기는 것. PC 사양마다 괜찮은 정도가 달라서 경고만 한다(사용자 결정).
- 여러 PC 를 원격으로 모니터링하거나 팀 공용 대시보드를 만드는 것.
- 에이전트에게 명령을 보내는 등 에이전트 자체를 조작하는 것.
- (Claude 판단) 토큰·요금 사용량 표시 — 논의되지 않아 첫 버전 범위 밖으로 둔다.
- (Claude 판단) WSL2·Docker·devcontainer 안에서 도는 에이전트·개발 서버의 워크트리 판별. 호스트에서는 중계 프로세스만 보여서 판별할 수 없다. 이런 포트는 목록에 "판별 불가"로 보여주되 정리 후보로는 절대 올리지 않는다.
- (Claude 판단, 나중 후보) 에이전트가 새로 저장한 메모리 보기, 여러 워크트리가 같은 파일을 고칠 때 미리 경고 — 대화 초반에 나왔지만 8개 목록에는 들어가지 않았다.

## 5. 반목표 (동작하더라도 이러면 실패)

- **확인 없이 무언가를 끄거나 지우는 것.** 포트 내리기·프로세스 종료·폴더 삭제는 항상 확인 창을 거친다. 자동 정리는 없다.
- 에이전트가 작업 중인 워크트리의 서버·프로세스를 정리 후보로 올리는 것.
- **다른 도구의 설정을 망가뜨리는 것.** Claude 설정 파일에 훅을 넣을 때 기존 훅(예: Orca 가 넣은 훅)을 보존하고, `statusLine` 은 건드리지 않으며, 연동을 끄면 pitwall 이 넣은 것만 정확히 걷어낸다.
- 회사 경로·사내 주소·계정 같은 정보가 레포에 들어가는 것. 프로젝트 고유 값은 전부 사용자 설정으로 뺀다.
- (Claude 판단) 감시하는 앱 자체가 무거워지는 것. **초기 목표치**: 창이 닫혀 있을 때 평균 CPU 1% 미만, 앱 전체 RAM 300MB 미만. 고정 값이 아니다 — 첫 빌드에서 실제로 재보고 조정한다. 수집 주기는 창이 열려 있을 때와 닫혀 있을 때 다르게 둔다.

## 6. 제약

- Windows + macOS.
- 공개 GitHub 레포 `yeonjin1357/pitwall`, MIT 라이선스.
- **코드 서명 없음.**
  - Windows 는 "알 수 없는 게시자" 경고가 뜨고, macOS 는 "확인되지 않은 개발자/손상된 앱" 경고가 뜬다 → README 에 설치 안내를 둔다.
  - macOS 는 서명 없이 자동 업데이트가 안 된다 → 새 버전은 수동 재설치. Windows 는 자동 업데이트.
- 작성자는 Windows 만 있다. macOS 동작 확인은 나중에 팀원에게 부탁한다(사용자 결정).
- **첫 릴리스부터 macOS 빌드를 함께 올리되 "macOS 미검증"으로 표시한다**(사용자 결정). 팀원 확인은 그 빌드로 한다. macOS 수집 코드는 Windows 와 같이 만든다.
- (Claude 판단) macOS 는 Apple Silicon 과 Intel 을 둘 다 지원한다.
- 프로젝트 고유 값(감시할 포트 범위, 무거운 명령 패턴, RAM 기준값, 미사용 기준 시간 등)은 코드에 넣지 않고 사용자 설정으로 둔다.

## 7. 사용자가 정한 방식

- **별도 데스크톱 앱**으로 만든다(Claude Code 플러그인이 아님). 여러 세션·도구에 걸친 정보라서 특정 세션 안에 넣지 않는다.
- **트레이(Windows) / 메뉴바(macOS) 상주.**
- **메인 창 = 카드 대시보드.**
  - 맨 위에 RAM 막대.
  - 아래 카드: 에이전트 · 포트 · 남겨진 프로세스 · 무거운 작업 · 디스크 · 메모리 경고.
  - 카드를 누르면 **그 자리에서 펼쳐지며** 목록과 정리 버튼이 나온다(화면 이동 없음).
- **트레이 아이콘 클릭 = OS 기본 메뉴.** RAM 요약, 에이전트 수(대기 수), 정리 후보 몇 개(바로 실행 항목), 앱 열기, 설정, 종료.
- **무거운 작업은 경고만, RAM 기준.**
- **배포:** 공개 GitHub 레포 → GitHub Actions 가 Windows·macOS 설치 파일을 빌드 → GitHub Releases 에 올린다.
- **세부 디자인·레이아웃은 확정하지 않는다.** 실제 데이터가 들어간 앱을 보면서 계속 다듬는다.
- **시각 디자인은 Claude 가 처음부터 만들지 않는다.** "AI 가 만든 티"가 나는 디자인을 피하기 위해, 이미 개발된 오픈소스 앱(허용 라이선스: MIT·Apache-2.0 등)의 디자인을 가져와 조금 변형한다. 가져온 출처와 라이선스 고지는 레포에 남긴다.
- **디자인 기반: Uptime Kuma** (https://github.com/louislam/uptime-kuma, MIT, Vue 3 + Bootstrap 5) — 실제 화면 3개 시안(Uptime Kuma / Podman Desktop / Beszel) 중 사용자가 골랐다. 같은 Vue 라서 스타일 코드(SCSS 변수·카드·상태 배지·하트비트 막대·다크 테마)를 직접 가져와 변형한다. 레이아웃은 위에서 정한 카드 대시보드를 따른다. 참고용으로 Stats(macOS 메뉴바 모니터)의 촘촘한 수치·미니 그래프 표현을 본다.

목업(구조 결정용, 비확정): 대화 중 브라우저로 본 화면 — A(카드 대시보드) 선택, 상세는 "그 자리 펼치기" 선택, 트레이는 "OS 기본 메뉴" 선택.

## 8. Claude 가 정한 것 (사용자 반대 없음, 언제든 바꿀 수 있음)

- **기술:** Electron + Vue 3 + TypeScript. OS 정보 수집·프로세스 종료는 Electron 메인 프로세스(Node)에서 한다. 팀이 매일 쓰는 기술이라 누구나 고칠 수 있다는 점을 앱 크기(Electron 은 RAM 200MB 안팎)보다 우선했다.
- **수집 방식 우선순위:** ① OS 기본 명령과 프로세스 명령줄 해석(예: 개발 서버 명령줄 안의 경로 → git 루트) ② Claude·Codex 세션의 작업 폴더는 훅 이벤트·세션 파일에서 얻는다. ③ 그래도 Windows 에서 꼭 필요한 정보(예: 다른 프로세스의 작업 폴더)가 안 나오거나 명령을 반복 실행하는 부하가 §5 목표를 넘으면, 작은 네이티브 헬퍼를 허용한다. 쓰게 되면 이유를 문서에 남긴다.
- **설정 위치:** 메인 창 오른쪽 위 톱니바퀴.
- **안 쓰는 포트 기준:** 기본 20분.
- **OS 알림 대상:** RAM 부족 / Claude 권한 대기 / 무거운 작업 겹침(RAM 기준). 항목별로 켜고 끌 수 있다.
- **Claude 연동:** 앱의 "Claude 연동 켜기"를 눌러야만 `~/.claude/settings.json` 에 훅을 추가한다. 훅은 이벤트를 pitwall 의 로컬 포트로 보낸다(Orca 가 쓰는 방식과 같은 구조). 끄면 원래대로 되돌린다.
- **Codex 연동:** 실행 중인 프로세스와 Codex 세션 파일을 보고 판단한다.
- **로그인 시 자동 실행:** 설정에서 켜고 끌 수 있게 하고, 기본값은 켬.
- **갱신 주기 설정:** 사용자가 "빠르게 / 보통 / 절약" 중에서 고를 수 있게 한다. 부하 목표치(§5)는 "보통" 기준이다.

## 9. 빌더에게 맡기는 것

- OS 별 수집 방법(열린 포트, 프로세스와 명령줄·작업 폴더, 포트별 접속 여부, RAM, 폴더 용량)과 갱신 주기.
- 프로세스 → 워크트리 판별 방법(작업 폴더·명령줄 → git 루트).
- "남겨진 프로세스" 판별 방법(프로세스 트리, 에이전트 세션 종료 시점 등).
- "끝난 워크트리" 판별 방법(머지 여부 확인 기준 브랜치 등).
- 설정 파일 형식·저장 위치, 상태 보관 방식.
- 패키징·업데이트 도구 선택, CI 구성, 테스트 전략.
- Codex 상태를 어디까지 알아낼 수 있는지 조사(훅 지원 여부 포함).

## 10. 알려진 위험

- Codex 세부 상태(권한 대기 등)는 알아내지 못할 수 있다.
- macOS 동작은 작성자가 직접 확인할 수 없다. 미검증 빌드가 공개 Releases 에 올라간다.
- 서명 없는 실행 파일을 회사 보안 프로그램(백신 등)이 막을 수 있다.
- Claude Code 훅 설정 형식이 바뀌면 연동이 깨질 수 있다.
- 프로세스를 잘못 판별해 엉뚱한 것을 정리 후보로 올리면 신뢰를 잃는다 → 판별이 불확실하면 후보에서 빼는 쪽으로 기운다.
